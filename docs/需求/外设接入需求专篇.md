## 1. 定位与边界

### 1.1 定位

外设接入层是**数据入口**，不是地图的一部分，也不是业务的一部分：

```
外设（多端口/多组播）
   │ UDP
   ▼
┌─────────────────────────────────────────────────────┐
│ 外设接入层（后端 C++ 独立模块）                       │
│  接入点 ACC → 解析器 PRS → 归一化 NRM → 健康 HLT      │
│                    │                    │            │
│              指令下发 CMD          进程内队列 FAN      │
└────────────────────┬────────────────────────────────┘
                     │ 统一信封 {type,data,ts}（复用既有 WS 通道）
                     ▼
        宿主前端（useStore → useMapData 适配器）
                     │ MapData / MapDraw（既有契约，不改）
                     ▼
        map-2d（纯渲染，不认识任何外设与协议）
```

**一句话分工**：接入层负责"**把各说各话的外设变成一份标准数据**"；地图模块负责"**把标准数据画出来**"；两者之间只有既有 WS 事件与 `MapData` 契约。

### 1.2 范围边界

| 边界 | 内容 |
|---|---|
| 🚫 不做渲染 | 接入层不接触 MapLibre / 地图数据源；"哪些设备上台、如何抽稀"属消费侧 |
| 🚫 不做业务 | 不含阶段流程、目标台账、威胁评级、链路状态机、界面 |
| 🚫 不做回放 | **本轮不做**历史存储与时序回放（决策 D1）；回放数据后续由宿主按 M2-DRAW-18 提供 |
| 🚫 不改地图模块 | `map-2d/` 源码与文档零改动；`useMapData.ts` 契约不变 |
| 🚫 不引中间件 | 队列用**进程内**实现，不引入 Redis / NATS / Kafka（决策 D2） |
| 🚫 不做设备管理界面 | 设备台账以接口与事件形式提供，界面由宿主决定 |
| 🚫 不做协议反向工程 | 未提供协议文档的设备类型，只支持"原始透传 + 标注"，不猜测字段语义 |

### 1.3 硬约束（来自既有契约）

| 约束 | 取值 | 依据 |
|---|---|---|
| 既有组播地址/端口 | `239.10.10.10:45454` | 契约 §1（本条接入点 MUST 继续可用，不得破坏） |
| 报文尺寸 | 单包 ≤ 8 KB（UTF-8） | 契约 §1 |
| 端口占位 | 后端 HTTP/WS `8080`、AI 桥 `8090` | 契约 §1；新增接入端口 MUST 避开 |
| WS 信封 | `{ "type": "...", "data": {...}, "ts": <epoch ms> }` | 契约 §4 |
| REST 响应体 | `{ "code": 0, "message": "ok", "data": {} }` | 契约 §2 |
| 时间 | 时间戳 epoch 毫秒；本地时间串 `YYYY-MM-DD HH:mm:ss` | 契约 §2 |

## 2. 已确认的输入约束（需求评审结论）

> 以下为需求确认阶段与提出方逐条确认的结果，是本专篇数值口径的来源。

| 项 | 结论 |
|---|---|
| 模块归属 | **后端 C++ 独立接入层**（不是地图模块内部，也不是前端模块） |
| 外设形态 | **多端口 / 多组播地址并行**，每类设备一套 |
| 协议差异 | 每类设备协议可不同 → **插件式解析器**（一设备协议一实现） |
| 规模 | ≈ **1000 台 × 1 Hz × 200 B** ≈ 200 KB/s（≈1.6 Mbps） |
| 报文序号 | 设备报文**带序号（seq）与时间戳** → 丢包率与乱序可**精确统计** |
| 队列 | **进程内队列**，无外部中间件，预留升级口 |
| 指令通道 | 接入模块**直接对外发 UDP**，回执也走 UDP，含超时重传 |
| 回放 | **本轮不做** |
| 上图策略 | **全量写 store**，渲染压力由 map-2d 既有降级策略承担（抽稀 / 聚合 / 标签上限） |
| 端到端延迟 | **P95 ≤ 500 ms**（设备发包 `ts` → 浏览器渲染完成） |
| 失联判定 | **可配置，默认 3× 上报周期**（1 Hz 设备即默认 3 s） |

## 3. 功能需求条目

### 3.1 接入点（ING-ACC）

> 一条"接入点"= 一个 `组播地址:端口` + 一个解析器 + 一个目标 topic。多类设备 = 多个接入点并行。

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ING-ACC-01 | **MUST** 多接入点并行接收：每个接入点含 `{ id, listen(地址/端口/网卡), parserId, topic, enabled }`，可同时存在多个（MUST 支持 ≥ 8 个接入点） | 同时开 3 个接入点分别发不同协议报文，三路数据均正确入库与广播，互不串台 | ⏳ |
| ING-ACC-02 | **MUST** 配置声明式：接入点全部来自配置文件/环境变量，不硬编码；未配置时回落既有 `239.10.10.10:45454`（单接入点）行为 | 删掉全部新增配置后，系统行为与现状一致 | ⏳ |
| ING-ACC-03 | **MUST** 运行时热增删接入点：不重启进程即可加入/移出一个接入点 | 运行中调 `POST` 新增接入点，10 s 内开始收到该端口数据；移除后不再收到且不报错 | ⏳ |
| ING-ACC-04 | **MUST** 故障隔离：某接入点 bind 失败 / join 组播失败 / 端口被占时，**其它接入点继续工作**，失败原因可读可查 | 故意占用某端口后启动，该接入点报可读原因，其余接入点数据正常 | ⏳ |
| ING-ACC-05 | **MUST** 报文边界处理：超过 8 KB 的包截断并计数告警；空包丢弃 | 注入超长包与空包后，接收循环不中断，计数正确 | ⏳ |
| ING-ACC-06 | **MUST** 接入点级运行指标：到达包数 / 字节数 / 丢弃数 / 解析失败数 / 最近到达时刻，可查询 | 调用指标接口能读到逐接入点计数，与发送端数量对得上 | ⏳ |

### 3.2 协议解析（ING-PRS）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ING-PRS-01 | **MUST** 解析器接口：`原始字节 → 归一化事件[]`（一个包可产出 0..N 个事件）；解析器**无状态、可重入** | 同一份字节重复喂入得到相同结果；单包产出多事件时全部到达 | ⏳ |
| ING-PRS-02 | **MUST** 插件式注册：解析器按 `parserId` 注册并被接入点引用；支持**编译期静态注册**；未注册的 `parserId` 拒绝该接入点启动并给出可读原因 | 新增一个解析器实现并注册后，接入点配置引用它即可生效，无需改接入层核心 | ⏳ |
| ING-PRS-03 | **SHOULD** 原始透传解析器：内置 `raw.passthrough`，把原始字节包成 `kind:"raw"` 事件（含来源地址、长度、十六进制摘要），用于协议未定的设备 | 用 `raw.passthrough` 接入一个未知设备，能收到带来源的 raw 事件且不影响其它接入点 | ⏳ |
| ING-PRS-04 | **MUST** 解析器异常隔离：解析器抛异常或崩溃只影响该接入点，**MUST NOT** 中断接收线程，**MUST NOT** 影响其它接入点；异常计数可查 | 挂一个必抛异常的解析器，其它接入点数据无中断（实测对比前后包数） | ⏳ |
| ING-PRS-05 | **MUST** 向后兼容：既有 4 种 `kind`（`uav.pos` / `link.quality` / `target.state` / `node.state`）纳入解析器体系，**WS 事件名与既有字段保持不变** | 既有前端代码零改动即可继续收到并处理这 4 类事件（回归对比事件体字段） | ⏳ |

### 3.3 归一化（ING-NRM）

> 归一化对象是接入层**对外唯一的数据形状**，也是接入层与地图/业务之间的合同。字段级定义见《外设接入契约》§2。

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ING-NRM-01 | **MUST** 统一标准对象：所有解析结果 MUST 归一为同一形状（`deviceId / deviceType / kind / lng / lat / alt / heading / speed / battery / seq / ts / quality / recvAt / source`）；缺失字段按契约降级，不报错 | 三种不同协议的设备数据归一后形状一致，字段缺失不导致异常 | ⏳ |
| ING-NRM-02 | **MUST** 坐标与单位统一：WGS84 经纬度、顺序 `[经度, 纬度]`、高度米、速度 m/s、航向 0–360 度；经纬度越界（`|lng|>180`、`|lat|>90`）或非数字只丢该字段并计数 | 注入越界/非法值，事件仍到达、非法字段被丢弃且计数增加 | ⏳ |
| ING-NRM-03 | **MUST** 时间戳策略：优先用设备报文 `ts`；缺失时用服务端到达时刻补齐，并以 `tsSource: "device"｜"server"` 标明来源（回放与延迟统计依赖此字段） | 分别注入带/不带 `ts` 的报文，`tsSource` 取值正确 | ⏳ |
| ING-NRM-04 | **SHOULD** 溯源信息保留：归一对象保留 `source`（接入点 id、来源 IP:端口、原始包长度），供排障；**不默认全量留存原始报文**（本轮无存储需求） | 排障接口能读到某设备的来源接入点与来源地址 | ⏳ |

### 3.4 设备健康（ING-HLT）

> 序号精度前提：设备报文**带 `seq` 与 `ts`**（评审已确认），因此丢包率与乱序为**精确统计**，不是估计。

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ING-HLT-01 | **MUST** 离线判定：某设备超过 `timeout = 心跳周期 × 倍数` 未上报即判离线并发事件；**倍数默认 3，可按设备类型配置** | 1 Hz 设备停发 3 s 后收到离线事件（实测停发→事件时延 ≤ 1 s 判定粒度）；改了设备类型的倍数后按新值生效 | ⏳ |
| ING-HLT-02 | **MUST** 恢复上线：离线设备再次上报时发上线事件，事件携带离线时长 | 停发→恢复后收到上线事件，时长与停发时间吻合（误差 ≤ 1 s） | ⏳ |
| ING-HLT-03 | **MUST** 丢包率统计：按设备（并按接入点聚合）统计**每窗口丢包率**：`(maxSeq - minSeq + 1 - 实收数) / (maxSeq - minSeq + 1)`，窗口长度可配置（默认 60 s） | 发 1000 包、故意跳过 100 个 seq → 统计丢包率为 10%（±0.1pp） | ⏳ |
| ING-HLT-04 | **MUST** 乱序统计：按 `seq` 判定乱序（后到包 seq < 窗口内最大 seq 即计一次乱序），给出乱序次数与乱序率；**设备无 `seq` 时 MUST 明确标注为"不可精确统计"而非给假值** | 按打乱顺序发 100 包 → 乱序计数与人为打乱数一致；去掉 `seq` 后统计接口返回"不可精确统计"标记 | ⏳ |
| ING-HLT-05 | **MUST** 设备台账：可查询全部已发现设备（`deviceId / deviceType / 首次出现 / 最近上报 / 在线状态 / 最近位置 / seq 与丢包统计`） | 三台设备接入后台账列出 3 条，字段完整；离线设备仍在台账中并标为离线 | ⏳ |
| ING-HLT-06 | **SHOULD** 健康事件上行：离线/上线/丢包超阈值事件经既有 WS 通道上行（复用 `node.state` / `alert` 事件名），宿主可据此告警 | 制造离线，前端能收到对应事件（事件名与字段见契约 §5） | ⏳ |

### 3.5 指令下发（ING-CMD）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ING-CMD-01 | **MUST** 下发接口：REST 入口接收指令（目标设备、指令类型、载荷），返回 `cmdId` | 下发后立即拿到 `cmdId`，指令进入 `pending` | ⏳ |
| ING-CMD-02 | **MUST** 发送通道：接入层直接对外发 UDP；单播（指定设备地址）与组播（指定接入点）两种方式，按设备/接入点声明选择 | 两种方式各发一条指令，目标端均收到正确字节 | ⏳ |
| ING-CMD-03 | **MUST** 回执确认：设备回执（含 `cmdId` 与 `ackSeq`）与在途指令匹配，匹配成功转 `acked`；**无法匹配的回执 MUST 计数上报**（不静默丢弃） | 发指令→回执→状态变 `acked`；伪造一个无主回执，计数 +1 | ⏳ |
| ING-CMD-04 | **MUST** 超时重传：超时时间、最大重传次数可配置（默认超时 1 s、重传 2 次）；重传耗尽转 `timeout` 并给可读原因 | 目标端不回执时，实测重传次数 = 配置值，最终状态 `timeout` | ⏳ |
| ING-CMD-05 | **MUST** 指令状态机与查询：状态取值为 `pending / sent / acked / failed / timeout`；可按 `cmdId` 查询状态与时间线（发出/重传/回执各时刻） | 查询接口返回状态与完整时间线，与实测时刻吻合 | ⏳ |
| ING-CMD-06 | **MUST** 操作日志：记录 谁（来源）/ 何时 / 向谁 / 发了什么 / 结果如何；可按设备与时间范围查询 | 下发若干指令后，日志接口能按设备过滤出全部记录且字段完整 | ⏳ |

### 3.6 分发（ING-FAN）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ING-FAN-01 | **MUST** 接收与广播解耦：归一化事件进**进程内队列**，由独立消费侧合并后经 `EventHub` 广播；接收线程 MUST NOT 因广播阻塞 | 客户端断网重连期间，接收计数持续增长（接收未被阻塞） | ⏳ |
| ING-FAN-02 | **MUST** 单帧合并：同一时间窗内同设备的多次上报合并为**最后一次**再广播（默认窗 100 ms，可配置，配 0 即逐包直发） | 窗内对同一设备发 10 次，客户端收到 1 次（值为最后一次）；配 0 时收到 10 次 | ⏳ |
| ING-FAN-03 | **MUST** 边界声明：接入层 MUST NOT 做"是否上台 / 抽稀 / 聚合"决策；这些属消费侧（宿主 + map-2d 既有降级策略） | 接入层代码中不出现地图类型、图层名、抽稀阈值 | ⏳ |

### 3.7 非功能性（ING-NFR）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ING-NFR-01 | **MUST** 吞吐：单机稳定承载 **1000 设备 × 1 Hz × 200 B**，接收侧零丢弃（以接入点计数与发送端数量逐包对比为准） | 模拟器按 1000×1 Hz 打 10 分钟：收包数 = 发送数（丢 0），无内存增长趋势 | ⏳ |
| ING-NFR-02 | **MUST** 端到端延迟：设备发包 `ts` → 浏览器完成渲染，**P95 ≤ 500 ms**（同机内网口径）；指标可查询 | 压测中采集 ≥ 1000 个样本，P95 ≤ 500 ms | ⏳ |
| ING-NFR-03 | **MUST** 热插拔不中断：运行中增删接入点，既有接入点 MUST NOT 丢包（增删前后对比既有接入点收包连续性） | 增删 3 次接入点，既有接入点零丢弃 | ⏳ |
| ING-NFR-04 | **MUST** 故障隔离：单解析器/单接入点故障不扩散（对应 ING-PRS-04 / ING-ACC-04），故障期间进程不退出 | 注入故障后进程存活、其它接入点数据不断 | ⏳ |
| ING-NFR-05 | **MUST** 资源上限：队列长度、设备台账条数、指令日志条数、各统计窗口均为**有界容器**，超限按最旧淘汰；提供占用查询与周期巡检（口径对齐 map-2d `core/resources.ts` 的既有做法） | 上限调小后灌数据，容器不超限且淘汰的是最旧数据；长跑 30 分钟资源不持续增长 | ⏳ |

## 4. 验收准则

**功能验收**

1. 三个接入点（不同端口 + 不同协议）并行运行，三路数据同时正确归一与广播，互不串台；
2. 运行中新增/移除接入点，既有接入点零丢弃；
3. 故障注入三项全部隔离：端口被占、解析器抛异常、非法报文；
4. 设备健康：离线/上线事件按时产生；丢包率与乱序在人为注入下与预期**精确一致**；无 `seq` 设备被标注为"不可精确统计"；
5. 指令：单播与组播各一条走通 `pending → sent → acked`；不回执场景走通 `sent → timeout`，重传次数 = 配置值；操作日志可查；
6. 既有回归：`239.10.10.10:45454` 与既有 4 类 WS 事件在**前端零改动**下照常工作。

**性能验收**

1. 1000 设备 × 1 Hz × 200 B 持续 10 分钟，接收侧零丢弃，进程 RSS 无持续增长；
2. 端到端延迟 P95 ≤ 500 ms；
3. 单帧合并开关两侧行为可复现（合并 = 1 次/窗，直发 = 逐包）。

**交付验收**

1. 接入点、设备类型、解析器绑定、超时倍数、重传参数**全部**来自配置（无硬编码）；
2. 指标与台账接口齐全（接入点 / 设备 / 指令 / 日志四类查询）；
3. 无外设环境下，模拟器 + 压测脚本可复现上述全部场景。

## 7. 风险与开放问题

| # | 风险 / 问题 | 影响 | 应对 |
|---|---|---|---|
| R1 | 设备协议文档仍可能缺失或变更 | 解析器需反复改 | 解析器插件化（ING-PRS-02）+ 原始透传（ING-PRS-03）；协议到位只换实现 |
| R2 | 1000 台全量上图时**标签渲染**是瓶颈（map-2d 实测：500 个标注使混合负载从 5.1 ms 升到 11.0 ms，标签避让是成本大头） | 端到端 P95 可能超 500 ms | 作为**观测项**：先用 `getStats()` 监控；超标时在**消费侧**加标签上限/抽稀（`setLabelPolicy` / 降级策略），**不改接入层** |
| R3 | UDP 无连接，组播在跨网段/多网卡环境下可能收不到 | 接入点静默无数据 | 接入点级指标（ING-ACC-06）+ 指定网卡配置（ING-ACC-01）+ 排障接口 |
| R4 | 1000 台 × 1 Hz 上探到 10 Hz（100×）时进程内队列与本机 SQLite 可能成为瓶颈 | 架构返工 | D2 已留升级口；日志落库按**采样 + 有界淘汰**（ING-NFR-05），必要时仅落状态变更 |
| R5 | 指令下发为单向 UDP，回执可能丢失导致"实际已执行但判 timeout" | 语义误判 | 状态机保留 `timeout` 与 `failed` 区分；操作日志记录重传全过程；涉及互斥动作仍由业务侧（契约 §2 `code=1002`）兜底 |
| R6 | 多接入点共用同一端口（SO_REUSEPORT）时的收包分配行为因平台而异 | 端口规划不当会重复收或漏收 | 文档明确"**一个端口只归一个接入点**"；同端口冲突在启动时报可读错误（ING-ACC-04） |
